# CGM glycaemic range features

Per-person continuous glucose monitoring features built by classifying every
CGM reading into one of five mutually exclusive glycaemic ranges.

Generated by:

```bash
.venv/bin/python src/add_cgm_ranges_to_full_person_aggregates.py
```

The script is idempotent — it drops any range columns it previously wrote
before re-merging, so it can be re-run safely.

---

## 1. Ranges

| Key | Label | Bounds (mg/dL) |
|---|---|---|
| `sev_hypo` | Severe hypoglycaemia | < 54 |
| `mod_hypo` | Moderate hypoglycaemia | 54 – 69 inclusive |
| `normal` | Normal | 70 – 180 inclusive |
| `mod_hyper` | Moderate hyperglycaemia | 181 – 250 inclusive |
| `sev_hyper` | Severe hyperglycaemia | > 250 |

The ranges are exhaustive and non-overlapping, so the five `frac_time` columns
sum to exactly 1 for every person (asserted by the script).

Every glucose value in this export is an integer, so the inclusive bounds above
are unambiguous. The implementation uses half-open `[lo, hi)` edges
`[-inf, 54, 70, 181, 251, inf)`, which reproduces the inclusive bounds exactly
for integers and additionally leaves no gap for a hypothetical fractional value.

---

## 2. Columns

30 columns are inserted after `days_tracked`: 5 data-quality columns, then five
metrics for each of the five ranges. The table goes from 2245 × 67 to 2245 × 97.

| Column | Definition | Empty-range value |
|---|---|---|
| `cgm_<range>_minutes` | Total time in range, minutes | `0` |
| `cgm_<range>_frac_time` | Share of the person's valid readings in range | `0` |
| `cgm_<range>_mean_mg_dl` | Mean glucose across readings in range | `NaN` |
| `cgm_<range>_windows_per_day` | Contiguous in-range episodes per tracked day | `0` |
| `cgm_<range>_sustained_windows_per_day` | As above, episodes ≥ 15 min only | `0` |

`cgm_<range>_mean_mg_dl` is deliberately `NaN` rather than `0` when a person
never entered the range — "average value while in range" is undefined, not zero,
and a `0` would corrupt any downstream mean or correlation. The episode counts
are genuinely `0` in that case, so they stay `0`.

The quality columns are described in §5.

---

## 3. How time is counted

The Dexcom G6 cadence in this dataset is a near-perfect 5 minutes: 99.94% of
consecutive within-person gaps are exactly 5.00 min, and only 0.01% exceed
60 min. Each valid reading is therefore credited with 5 minutes of time.

This makes counting readings and integrating timestamps agree to within
rounding, and it avoids the failure mode of naive timestamp integration, where a
multi-hour sensor dropout gets attributed entirely to whichever range the last
reading before the gap happened to fall in.

`frac_time` is the standard consensus time-in-range quantity: readings in range
divided by all valid readings for that person.

`windows_per_day` divides by `days_tracked` (count of distinct UTC dates with at
least one reading), the same denominator the repo already uses for
`avg_spikes_per_day`.

---

## 4. How windows are counted

A **window** is a maximal run of consecutive readings in the same range. A run
is broken by either a range change or a sampling gap exceeding
`MAX_GAP_MINUTES = 10.0`, so a sensor dropout never silently bridges two
separate episodes.

Runs are counted **strictly**: a single reading crossing a range boundary does
split a window. This is a deliberate departure from
`src/glucose_spike_detection.py`, which folds a lone sub-threshold reading back
into a spike (`MAX_DIP_READINGS = 1`). That tolerance exists because spike
detection thresholds on a single cutoff (140 mg/dL), where a one-reading dip is
usually sensor noise. Here the five ranges are exhaustive, so every boundary
crossing is a genuine transition between named clinical states rather than noise
around one cutoff.

### Sustained episodes

Strict counting means glucose hovering on a boundary registers as many separate
episodes. `cgm_<range>_sustained_windows_per_day` is the smoothed variant: it
counts only episodes lasting at least `MIN_EPISODE_MINUTES = 15.0` (3 readings
at the 5-minute cadence), the usual clinical convention for calling an excursion
an event.

It filters which episodes are **counted** and deliberately does not alter
`minutes`, `frac_time`, or `mean_mg_dl` — time spent in a brief excursion was
still time spent in that range. The two columns answer different questions: how
often glucose *touches* a range, versus how often it *settles* there.

The gap between them is large, and largest for hypoglycaemia:

| Range | Episodes/day (all) | Episodes/day (≥15 min) | Share under 15 min |
|---|---|---|---|
| `sev_hypo` | 0.100 | 0.056 | 44.6% |
| `mod_hypo` | 0.418 | 0.180 | **56.8%** |
| `normal` | 2.008 | 1.761 | 12.3% |
| `mod_hyper` | 1.878 | 1.510 | 19.6% |
| `sev_hyper` | 0.366 | 0.290 | 20.8% |

Over half of moderate-hypoglycaemia "episodes" and nearly half of severe ones
are brief boundary touches. Hypoglycaemia excursions in this cohort are mostly
transient dips rather than sustained events, so the strict count substantially
overstates episode burden at the low end. Prefer the sustained columns for any
hypoglycaemia event-rate analysis.

Note that `sustained_windows_per_day` can be `0` while `windows_per_day` is
positive — every excursion the person had was shorter than the minimum. That is
a meaningful value, not missing data.

## 5. Data quality: sentinel readings drive the tails

Dexcom reports `"Low"` / `"High"` strings for values outside sensor range.
Following the convention already used across this repo, they are mapped to
39 and 401 mg/dL, which places them in severe hypoglycaemia and severe
hyperglycaemia respectively.

There are 39,632 such readings (0.64% of 6.19M), but they are heavily
concentrated in a few participants and they dominate the extremes of these
features. Five columns expose this so unreliable participants can be filtered
by rule rather than by hardcoded `person_id`:

| Column | Definition |
|---|---|
| `cgm_n_readings` | Usable readings after cleaning and dedupe |
| `cgm_low_sentinel_frac` | Share of readings reported as `"Low"` |
| `cgm_high_sentinel_frac` | Share of readings reported as `"High"` |
| `cgm_short_wear` | `cgm_n_readings < 288` (one full day at 5-min cadence) |
| `cgm_quality_suspect` | `cgm_short_wear`, or `cgm_low_sentinel_frac > 0.5` |

### Why "Low" and "High" are treated differently

A high `"Low"` share is a **malfunction** signal. Three participants are
77–100% `"Low"` across only 28–75 readings:

| person_id | `cgm_n_readings` | `days_tracked` | `cgm_low_sentinel_frac` |
|---|---|---|---|
| 1111 | 28 | 2 | 1.000 |
| 7008 | 39 | 2 | 0.949 |
| 7052 | 75 | 2 | 0.773 |

Each has essentially every reading pinned at the floor. A person is not below
54 mg/dL for two days, so this is a failed sensor.

A high `"High"` share is instead a **censoring** signal. Five participants
exceed 50% `"High"` (4276 at 87.9%, 4295 at 59.6%, 1318 at 59.1%, 4395 at
55.5%, 1154 at 50.9%) and 33 exceed 10% — but these have full wear, roughly
2,500–2,856 readings over 10–11 days, so sustained severe hyperglycaemia is
clinically plausible. Their `cgm_sev_hyper_mean_mg_dl` is capped at the 401
ceiling and understates true exposure.

Filtering these people out would discard real signal, so `cgm_quality_suspect`
deliberately does **not** key on `cgm_high_sentinel_frac`. Threshold that column
yourself if censoring matters to your analysis.

### Effect of the filter

`cgm_quality_suspect` flags 8 of 2245 participants — the 3 failed sensors above
plus 5 more with under a day of data (1504, 4034, 7009, 7435, 7644). Dropping
them pulls `cgm_sev_hypo_frac_time`'s maximum from an implausible **1.000 down
to 0.210**, while leaving the genuinely hyperglycaemic participants in place.

```python
df = df[~df.cgm_quality_suspect.astype(bool)]        # drop failed / thin sensors
df = df[df.cgm_high_sentinel_frac <= 0.10]           # additionally drop censored means
```

## 6. Duplicate timestamps are a daylight-saving artifact

960 rows share a `(person_id, timestamp_utc)` key with another row. These are
**not** repeated measurements of the same instant, and they are not random:

- They fall on exactly two dates, **2024-03-10** and **2025-03-09** — the two US
  daylight-saving spring-forward dates in the study window.
- 80 participants are affected, and every one contributes exactly 24 rows:
  12 timestamps × 2, i.e. **exactly one hour**.
- The duplicated window spans local 23:00–03:00 across the transition.
- Each pair holds two *different* real readings (921 of 960 pairs disagree;
  e.g. person 1161 at `09:04:11` has both 109 and 122 mg/dL).

So an hour of genuine CGM trace was collapsed onto one set of timestamp labels
by a DST bug in the upstream timestamp conversion. Both readings are real, but
the hour is double-labelled.

Both this script and
`src/add_mean_cgm_overall_to_full_person_aggregates.py` drop duplicates keeping
the **first occurrence in file order** — deduped before sorting, so which row
survives does not depend on sort stability and the two scripts provably keep the
identical row set. Keeping both would count that hour twice in time-in-range;
dropping one loses 12 readings per affected person, 0.4% of their record.

This resolves a previous inconsistency: `mean_cgm_overall_mg_dl` formerly did
not dedupe, so it disagreed with these columns for those 80 people by up to
0.35 mg/dL. After the fix, a time-weighted average of the five
`cgm_*_mean_mg_dl` columns reproduces `mean_cgm_overall_mg_dl` to 6e-14 for
every participant.

If you would rather preserve all 6,194,153 readings, the alternative is to
re-space the duplicated hour onto a true 5-minute grid rather than dropping
half of it. That was judged not worth it here: it affects 3.6% of participants
for 0.4% of their record.

## 7. Validation performed

- The five `frac_time` columns sum to 1.0 for all 2245 persons (asserted in the
  script on every run).
- `cgm_<range>_mean_mg_dl` is `NaN` exactly when `cgm_<range>_minutes` is 0, and
  `windows_per_day` is strictly positive whenever time was spent in range
  (asserted on every run).
- `sustained_windows_per_day` never exceeds `windows_per_day`, and is 0 for
  ranges never entered (asserted on every run).
- All 25 range columns were recomputed by independent brute-force loops over
  raw readings — 12 sampled persons for the time/fraction/mean columns and 14
  for both episode counts: 0 mismatches.
- `days_tracked` recomputed from raw readings matches the pre-existing column
  for all 2245 persons.
- Coverage is 100% — all 2245 persons in the aggregates table have CGM data.
- `mean_cgm_overall_mg_dl` is the only pre-existing column these scripts alter
  (deliberately, see §6); the other 66 are byte-identical after the merge.
- Running both scripts repeatedly reproduces the file exactly. Reads use
  `float_precision="round_trip"` because pandas' default CSV float parser is up
  to 1 ULP off from `strtod`, which otherwise let untouched columns drift in the
  14th significant digit as scripts rewrote this file in place.
